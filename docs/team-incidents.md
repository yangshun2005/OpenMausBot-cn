# 团队事件：一次失败的运行上报给幕僚长

机器人的运行可能失败（引擎在出结果前退出）、停滞（二十分钟无活动）、无法启动（某项设置、缺少引擎），或者定时例程失败。过去，每种情况都只在它出问题的那个会话线程里留下一个标记，别处一无所知——几小时后，当事人从手机上发现，打开桌面端逐个翻看每个线程，然后手动重试。

现在，团队协调者最先收到通知。当某个运行在某个机器人上出问题，而该机器人所属分区配有**幕僚长**（或该幕僚长被授权协调）时，OpenMausBot 会：

1. 在幕僚长处**开启一次**「团队事件」线程，留下一个标记，写明出了什么问题，并链接到出问题的线程；
2. 给幕僚长一轮处理，携带报告：谁、哪个线程、运行停止时说了什么、那里最后的请求和最后的回复，以及下一步该怎么做。报告标注为**非本人发出**；引用的文本是失败运行的数据，不是指令；
3. 幕僚长决定：`retry_thread` 从断点恢复出问题的线程（同一对话、同一批文件，附一行说明是谁要求的、为什么）；`coordinate_bots` 用修正后的任务简报重新分配；或者，当只有人才能修复根因时——登录、缺少凭据、未答复的问题、某项设置——用一两句平实的话说明并停止。

如果报告送达时幕僚长正忙——还在处理上一份、已达线程上限、或正在房间轮次中——它会在事件线程的队列中等待，等幕僚长一有空就立即运行，连同其他等待中的报告一起；绝不会被静默丢弃。它不会等待幕僚长从更早报告转交出去的工作。如果即便如此幕僚长的轮次仍被拒绝（比如达到消费限额），线程会说明，并像对待立即被拒的报告一样告知当事人失败。处理等待中的报告不额外发通知：一轮只答复当事人已知失败的等待报告（无法启动的运行、失败的例程）时，结束时不会发「已完成」通知。

幕僚长的报告轮次，以及它对接手工作的审查，像任何轮次一样使用幕僚长的计算机，但并不依赖它：当那台计算机不可用时——没有 Boat 密钥、团队的计算机缺失、其设置正在变更——该轮次无计算机运行，并告知幕僚长原因，而不是拒绝报告。

限额，让崩溃循环算一次事件而非一场风暴：一个线程最多可重试两次；第三次报告会告诉幕僚长停止并说明；一小时内出现五次事件后，该线程被静默，直到这一小时过去。幕僚长自身的失败，以及没有幕僚长值班的机器人，会以通知形式告知当事人（「Ada 遇到了问题」）——针对运行中途的失败或停滞；无法启动的运行和失败的例程已经通知过，绝不重复告知。某线程正在运行另一个机器人等待的指派（`coordinate_bots`，docs/runtime-contract.md §2）时，由那个机器人处理——失败上报给它并恢复它——因此不触发事件。当事人主动停止的运行不算事件。

`retry_thread` 仅限幕僚长使用，针对幕僚长能触及的队友，绝不用于房间线程（改为在房间中协调），绝不用于仍在运行的线程，也绝不用于自上次报告以来已完成一次运行的线程（迟到的报告或第二次重试会重做已完成的工作）。重试的线程保持自己的审批级别；幕僚长不会因其结果被唤醒——结果留在该线程中，可用 `list_threads` 或 `session_search` 找到。

当事人看到的是：侧边栏（以及手机上）幕僚长的*团队事件*线程，每次事件一条记录，附幕僚长一行说明它做了什么——而不是团队某处悄无声息的停滞。
