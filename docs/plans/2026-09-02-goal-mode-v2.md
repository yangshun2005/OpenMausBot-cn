# Goal 模式 v2 — 持久化目标、忙碌安全的房间运行、`/goal`、例程触发器

状态：计划 + 实现进行中（2026 年 9 月 2 日）。不取代任何内容；扩展 #617/#661 中交付的有界目标驱动团队运行，并与 #690 中的委托唤醒工作组合。

## 为什么

三条社区反馈，均针对当前 main 真实存在：

1. **“如果房间中被要求为某个目标做贡献的 agent 正忙，目标会立即失败。”**
   属实。`runGroupMemberTurn` 有两个忙碌门控，它们会追加一个“本轮跳过”的标记并返回，而不设置 `orchestration.result.outcome`；随后 `runGroupGoalOperation` 读取 `outcome !== "settled"`，无法区分*忙碌*和*provider 崩溃*，于是将运行判定为 `failed`。这是代码库中唯一将忙碌视为致命的编排路径——委托会重试 3 次并在 settle 时唤醒，`ask_bot` 降级为委托，例程等待一个 tick，忙碌频道发送会排队（#661）。一个卡在别处权限卡片上的 bot（`waiting-on-you`）同样会杀死目标运行。
2. **“/goal 模式会让行为更接近 Grok Bot。”** 如今的目标模式是一次性的编辑器开关，仅限房间（1:1 会以 400 拒绝），一次发送就是一次 13 轮运行，以 `limit-reached` 和“再次发送目标”结束。目标不是持久对象：它存在于内存中的 `GroupTurnOperation` 里，重启会静默丢失；没有实时进度（`working` 卡片状态存在但从未发出）。
3. **“通过例程触发目标。”** 例程针对单个 bot 的分离任务；没有任何东西携带房间或模式，运行完成以第一个 `turn.completed` 为键。

## 我们借鉴什么（以及从哪借）

- **忙碌时停靠并恢复，绝不失败** — 我们自己的 `delegations.ts`（`waitingOnBusy`、有界尝试、每次空闲释放时 `retryDelegationsWaitingOn`）和 `steer-queue.ts`（将唤醒键设为“这个 *bot* 空闲”，因为房间中忙碌的 bot 会在不同线程上 settle）。Hermes 的 `heartbeat.py`/`goals.py` 清晰地陈述了该不变量：*在会话下次空闲时触发一次，绝不堆积积压*。
- **单 bot 的 Ralph 循环** — Hermes 的 `hermes_cli/goals.py`（其 `/goal`，本身改编自 Codex CLI 的）：一个常驻目标、每轮判定 `done | continue | wait`、一条普通续接消息（不修改系统提示）、带自动暂停的轮次预算、用户消息抢占并暂停、判定器故障时 fail-open、连续失败自动暂停，以及一个**不消耗轮次即可停靠的 wait 判定**。Hermes 无法通过 `hermes acp` 为我们运行这个循环（适配器中没有 `goal` 命令），因此该循环位于宿主侧且与引擎无关。
- **结构化完成 + 停止条件** — Hermes 的完成契约（`outcome`、`verification`、`constraints`、`boundaries`、`stop_when`）、质量门，以及“重复相同分配 ⇒ 阻塞”（房间已有最后一条）。
- **多 agent 工作的看板语义** — Hermes kanban：生命周期真相存在于一条持久记录中；worker 执行但从不拥有状态；每次交接都是一行人类可读的记录；从未心跳的认领会回收，死掉的 worker 会被清理，搁浅的任务会被诊断——而不是静默丢弃。

## 设计

### 1. 持久化 Goal 记录（`server/goals.ts`、`~/.openmausbot/goals.json`）

```ts
interface GoalRecord {
  id: string;
  kind: "room" | "bot";
  groupId?: string; botId?: string; threadId: string;
  goal: string;
  status: "working" | "waiting" | "paused" | "completed" | "needs-input" | "blocked"
        | "limit-reached" | "stopped" | "failed";
  turnCount: number; maxTurns: number;
  coordinatorBotId?: string;              // rooms
  waiting?: { onBotId: string; since: number; attempts: number; instruction?: string };
  detail?: string;                        // last visible progress line / terminal reason
  receiptMessageId: string;               // the live `goal.run` card, patched in place
  source?: { routineId: string; runId: string };
  createdAt: number; updatedAt: number; finishedAt?: number;
}
```

像 `delegations.json` 一样用 `atomic.ts`（0o600）写入。`goal.run` 转录卡片在开始时以 `status: "working"` 发出，并**每轮修补**（轮次数、协调者的可见详情、“等待 X”），而不是只在结束时追加。启动时，任何仍为 `working`/`waiting` 的目标变为 `paused`，详情为“OpenMausBot 已重启——恢复以继续”：目标文本保留，重启后不会有任何东西无人值守地运行。

### 2. 房间：忙碌是等待，不是失败

- `GroupMemberTurnOutcome` 新增 `"busy"`；`runGroupMemberTurn` 中的两个门控都设置它，目标步骤**不**计入该轮。
- Worker 忙碌 → 标记“等待 X 完成手头的事”，目标 `status: "waiting"`，`waiting.onBotId = X`，协调者待处理的分配保留在记录上，房间操作被释放（房间变为可用，`finishGroupTurnOperation` 不再自动使等待中的目标失败）。
- 唤醒：`turn.completed` 订阅者和每个显式空闲释放已经调用 `retryDelegationsWaitingOn(botId)`；同一钩子现在也恢复等待该 bot 的目标。恢复通过 `groupQueues` 重新进入（绝不自由运行），携带相同目标的新操作，从 worker 步骤继续。
- 边界：`attempts` ≤ 3 个不同的忙碌时段，外加墙钟时间上限；耗尽时，协调者会收到“X 无法腾出时间——重新分配或报告阻塞”作为下一条指令，而不是运行失败。协调者忙碌以相同方式停靠（它是运行无法绕过的唯一 bot）。
- `provider_failed` / `stalled` / `timed_out` 在 `failed` 前每步重试一次。

### 3. `/goal` 作为一等命令（房间和 1:1）

编辑器：`/goal <text>` = 目标模式发送（房间：今天的协调者运行；1:1：bot 目标）。`/goal status | pause | resume | stop` 映射到 `/api/goals/:id`。编辑器开关保留为可发现的形式；命令是可脚本化的形式。

**1:1 bot 目标循环**（宿主侧 Ralph 循环，`server/bot-goal-run.ts`）：第一轮将目标文本作为普通消息运行。每轮的指令要求 bot 以房间使用的相同私有 `<openmaus-goal>{status}</openmaus-goal>` 信封结尾（`continue | completed | needs-input | blocked`），由现有折叠从转录中剥离。在 `turn.completed` 时：解析 → `continue` ⇒ `startTurn(botId, continuationPrompt, { threadId, cardContinuation: true })`；终止 ⇒ 完成。没有辅助判定模型：自报告 + 预算 + 卡住检测与引擎无关（Claude、Codex、ACP 皆可）。保障措施镜像 Hermes：缺失信封 = 继续并轻推，连续 3 次缺失 ⇒ `paused`；相同回复摘要两次 ⇒ 轻推，三次 ⇒ `blocked`；`maxTurns` 20 ⇒ `limit-reached`（恢复会重置计数器）。目标中途的用户消息会抢占：目标在该轮暂停并在之后重新评估（steer-queue 已在 bot 空闲时投递消息）。续接只会在 bot 空闲时触发，绝不堆积。

**“更接近 Grok Bot”实际意味着什么**（已验证）：Grok *Bot* 没有目标原语——其长时运行感来自持久 bot + 关闭应用后仍存活的后台轮次 + 只停止匹配操作的审批 + 例程。人们记得的 `/goal` 是 Grok *Build* 的（xAI 的编码 agent，以 Apache-2.0 开源为 `xai-org/grok-build`，`crates/xai-grok-shell/src/session/goal_*`）。我们现在取得的一致性：

- **暂停是一种分类，不是失败。** `status: "paused"` 携带 `reason: "user" | "no-progress" | "budget" | "infra" | "blocked"`；每个原因都可恢复，卡片会说明是哪一个。未知或损坏的状态恢复为 `paused`（原因 `infra`），绝不自行驱动。
- **过早停止检测器。** 当信封说 `continue` 但可见回复以交回短语结尾（“Stopping here”、“Ready for review”、“Let me know if…”、“Please run … for me”、“I can't proceed without…”）时，下一次续接会点名它并再次轻推，而不是结束——目标轮不是聊天轮。（Grok Build 的 `goal_stop_detector.rs`。）
- **限速的进度帧。** 记录变化时广播的 `goal` 帧被合并为每个目标每秒最多一次（Grok Build 的 `GoalUpdated`），卡片显示状态、轮次/预算、最后详情和暂停原因。

**谁可以改变什么**（借自 OpenClaw 的 `/goal`）：模型的信封可以报告 `continue | completed | needs-input | blocked`；只有操作者（UI/API）可以 `pause`、`resume` 或 `stop`。`needs-input` 立即接受（这是给人类的问题）。第一次 `blocked` 会以轻推回应（“说出确切的阻塞点并尝试一个替代方案”）；只有当下一轮再次报告相同阻塞点时，`blocked` 才被接受——困难不是阻塞。

**卡住启发式**（OpenHands 阈值，范围限定为自上次用户消息以来的轮次）：相同回复摘要 ×3 ⇒ `blocked`（×2 时轻推）；相同工具调用 + 相同结果 ×4 ⇒ 轻推，然后 `blocked`。卡住本身绝不结束目标——记录的状态决定，恢复会重新检查真实状态（“检查当前工作区；不要依赖记忆”）。

**目标不是调度器**（OpenClaw/Hermes）：目标是附加到对话的一个持久目标。例程、心跳和 webhook 向携带目标的对话注入*轮次*；它们绝不 fork 或复制它。启动或恢复目标需要空闲对话，并会说“忙碌——等 X 完成后重试”，而不是创建一个非活动目标（OpenClaw）——房间除外，在那里等待就是特性，目标停靠在忙碌成员上。

**无进度守卫**（借自 Claude Code 的 `/goal`）：自报告的模型可以永远声称 `continue` 而什么都不做。harness 能看到每个工具事件，因此连续 N 个零工具调用的续接轮（N = 3）会暂停目标，详情为“无进度——以更多方向恢复”。这是确定性兜底；信封是模型的意见。目标等待长时工作时的空闲检查遵循相同形态（有界次数、倍增间隔），如果/当 1:1 目标学会在后台进程上 `wait` 时。

### 4. 例程可以启动目标

`Routine.target?: { kind: "bot" } | { kind: "room"; groupId; mode: "chat" | "goal" }`（缺省 = bot，向后兼容）。`RoutineManagerOptions` 新增 `startGroupRun(groupId, prompt, mode, trigger)`，返回 `{ threadId, goalId? }`；tick 的忙碌门控对房间目标变为 `groupIsWorking(group)`（一个会等待的运行——我们想要的语义，无需新机制）；目标运行的完成以目标记录达到终止状态（`onGoalFinished`）为键，而不是第一个 `turn.completed`。例程编辑器获得目标选择器；`propose_routine` 增加相同字段。

### 5. 后续（不在本批）

**独立验证**（Grok Build）：在目标可以完成之前，由非实现者的评估者决定——先是每轮隐藏评估者（`continue | candidate_complete | blocked{key}`），然后在 `candidate_complete` 时由一个小型对抗性验证者小组（默认反驳、多数投票，反驳标记为 `contradiction | unverifiable` 时暂停等待人类决定）。在 OMB 中，这是同一 bot 上带验证者提示的全新分离任务；可改编并注明出处的模板：`session/templates/goal_verifier_prompt.md`、`session/goal_evaluator.rs`、`session/templates/goal_continuation_directive.md`、`session/goal_stop_detector.rs`。
**目标开始时的冻结计划契约**（Grok Build `goal_planner_prompt.md` + Hermes 契约）：类型、3–5 条以结果陈述的门控验收标准、验证计划、非目标、清单；下一步轻推从第一个未勾选项挖掘。**预算**：带进度条的 token 预算，以及验证运行上限。

**房间目标的进度账本**（Magentic-One）：扩展协调者的信封，加入 `progress: "yes" | "no"` 和 `looping: true | false`；harness 为每次运行保留停滞计数器（无进度或循环 +1，有进度 −1），在 3 次停滞时，给协调者一条重新计划指令（“陈述已知内容、出了什么问题，以及新计划”），而不是另一次分配。记录上的 `last_progress_at`（AG2）驱动陈旧运行诊断，方式与 Beads/Gas Town 暴露搁浅工作相同。

记录上的完成契约 + 质量门；`start_goal` / `goal_status` MCP 工具，以便 Chief of Staff 可以打开和检查目标；重启后原地恢复；轮次预算之外的花费上限；iOS 伴侣中的目标运行回执。
