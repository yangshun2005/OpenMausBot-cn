# 感知线程的机器人

PM 机器人应该能对 QA 机器人说"为每个仍在等待 QA 的 Pull Request 开一个线程"，每个线程都应成为 QA 机器人上一个真实、可见、独立运行的线程，PM 机器人能看到每个线程的进展。如今机器人根本无法创建线程——无论在自己身上还是在队友身上——而且它并不知道自己做不到。

## 发生了什么

用户让一个机器人"为每个等待你审查的开放 PowerPM 创建一个新线程"。机器人却开了三条工单评论，被追问时才正确地解释：它没有可调用的动作来创建 OpenMausBot 线程，那些线程来自单独的用户提示。它对代码的判断是对的，但猜测是错的；问题在于事先没有任何东西告诉它这两件事。

## 代码现状（main 922715f，0.1.69）

- **线程已存在且独立运行。** #981 把 Tasks 变成了面向用户的 Threads：一个机器人最多同时运行三个直接线程（设置 → 通用 → 并行线程，1–10），每个线程有自己的模型、审批偏好、未读状态、工作目录和停止按钮。多余的消息在输入框上方排队，直到有空位。见 `docs/plans/2026-09-09-independent-threads.md`。
- **只有人能开线程。** `POST /api/bots/:id/tasks`（server/index.ts 约 12309 行）接收标题和可选文件夹，总是为调用者激活新线程，且位于所有者会话之后。没有内部端点，也没有对应的 MCP 工具。
- **每条对等消息都落在目标的活动线程里。** `runDelegatedTurn` 读取 `store.bot(toBotId)?.threadId`（server/index.ts 约 3816 行），`ask_bot` 也派发到同一处。向一个机器人发十条委派，就是十个回合排在某个人恰好正在看的那个线程里，与他们的对话交错。 #981 构建的三槽并发从未被机器人间的工作用到。
- **委派账本是按委派而非按线程记录的。** `check_delegation` 和 `wait_delegation` 以委派的任务 id 为键；发起委派的机器人能查询某一次交接，但无法列出"我昨天开的那些 QA 线程"，也看不到它们的未读和运行状态。
- **机器人的提示词从不提及线程。** 名册、房间提示词和工具描述谈的都是机器人、房间和委派。被问到线程的机器人除了这个词本身，没有任何可推理的依据。
- **扇出在其他地方已有速率限制。** `create_bot` 的 `MAX_CREATED_PER_TURN = 4`、`MAX_ROOM_POSTS_PER_TURN = 3`、委派的 `MAX_QUEUED_PER_THREAD`，以及房间发帖预算。线程创建需要同样的形态。
- **线程标题已有上限**，在 `store.createTask` 中为 80 字符， #983 又在 HTTP 边缘进一步截断创建的标题。机器人撰写的标题必须经过与名称和标题相同的扁平化处理（`fitsOnOneLine`）。

## 要构建什么

agents 代理上的三个工具、一个账本扩展、一行提示词，以及让它诚实的 UI 归属标注。

### 1. `list_threads`

返回调用机器人自己的线程，以及每个可达对等方的、**由调用者开启的**线程（见下方归属规则）。每行包含：线程 id、机器人、标题、状态（`running | waiting-on-you | queued | idle`）、对人的未读状态、最后活动时间，以及若有关联的委派 id。绝不返回对等方的私有线程：可见性规则是"你只能看到你开启的线程，加上你自己的"。与 `list_bots` 相同的分区和允许列表检查。

### 2. `start_thread`

```
start_thread({ bot_id?, title, message, folder? })
```

- 省略 `bot_id` 即在自己身上开线程。指定对等方则是委派到该对等方的一个**全新**线程：`delegate_bot` 强制的一切原样适用（分区、`peers` 允许列表、`approvePeerComms` 卡片、无人值守继承、深度上限、`MAX_QUEUED_PER_THREAD`），回复通过同一账本返回，因此 `check_delegation` 和 `wait_delegation` 对返回的 id 有效。
- 新线程以 `activate = false` 创建。 #981 的规则——选择线程绝不重定向正在运行的工作——也意味着机器人绝不能切换人正在看的内容。线程作为新行出现在侧边栏该机器人下方；人想看就自己打开。
- 第一条消息就是 `message`，当开启者是另一个机器人时，会包上现有的对等来源说明。
- 并发取决于目标机器人的并行线程设置。一个设置为三的机器人上开十个 PR 线程，意味着三个运行、七个按顺序在现有队列中可见地等待。工具结果会说明这一点："已开启；现在运行 3 个，这个是队列中第 4 个"。
- 上限：代理上的 `MAX_THREADS_PER_TURN = 5`，与机器人和房间发帖同样的精神，拒绝时告诉模型不要重试，并说明它还想开哪些。一个人要十二个，会分三个回合得到十二个，或者机器人说明它没开哪九个。
- 标题经过 `fitsOnOneLine` 和 80 字符上限；文件夹必须属于目标机器人。

### 3. `close_thread`（刻意做小）

把调用者开启的线程标记为完成，即侧边栏的空闲状态加上该线程中的最后一个活动标记。不删除：删除仍是人的确认操作。开了十个 QA 线程的 PM 机器人可以清理那些已读过回复的线程。

### 4. 账本：线程携带其开启者

`TaskRecord` 增加 `openedBy?: { botId, name, delegationId?, at }`。随任务持久化，在传输结构中导出，显示在侧边栏行和 iOS 上，作为一个小标签"由 Scout 开启"。这是 `list_threads` 作用域划分得以实现的基础，也是人信任一个并非自己开启的线程所需要的。备份像 `peerPost` 和 `peerAsk` 一样复制它。

### 5. 提示词告诉机器人线程是什么

一段话，随 agents 工具一起挂载：

> 线程是一段对话，有自己的历史和自己的运行；一个机器人可以同时运行多个线程，人会把它们看作该机器人下方的行。用 `start_thread` 在自己身上开一个线程做独立工作，或在队友身上开一个，交给他们一项应独立运行的任务。用 `list_threads` 查看你开启的那些线程进展如何。不要用工单评论、笔记或房间发帖来替代线程。

最后一句就是针对那张截图的修复。

### 6. 通知与静默

机器人开启的线程在需要人之前都是内部工作，完全遵循 #773 的规则：开启时不显示徽章、不推送；对等方的卡片、接管或提问仍会突破，并深链到该线程；完成只报告一次，由开启者恢复的回合报告，绝不重复。人在侧边栏打开的线程，行为与他们读过的任何线程一样。

### 7. 线程可从聊天中链接

当机器人在回复中把线程标题写成 `#Title` 时，记录会将其渲染为打开该线程的链接：选中机器人、切换到该线程，绝不重定向正在运行的工作。解析方式与 @提及一致：词首、最长已知标题优先、不区分大小写、仅限人实际能看到的标题，绝不匹配 `#123` 式数字或 Markdown 标题。机器人开启线程时留下的标记携带结构化的 `threadRef`，与机器人⇄机器人交换标记一样是可点击的胶囊，即使隐藏了工具调用也可见。手机端解码两个字段，显示开启者标签，并通过它们已有的切换路由点击进入该线程。

## 顺序

1. `TaskRecord` 上的 `openedBy`、传输结构、侧边栏和 iOS 标签、备份往返。
2. 先在自己身上、再通过对等方路径实现 `start_thread`；账本、门控和上限；代理测试，外加一个端到端测试：用假 CLI 在一个设置为两个槽位的对等方上开三个线程，断言其中一个排队。
3. `list_threads`，带开启者作用域规则，以及一个权限测试，确保对等方的其他线程绝不出现。
4. 提示词段落；一个测试，确保 "start_thread" 这些字出现在 1:1 和房间系统提示词中。
5. `close_thread`。
6. 桌面端和移动端的 `#Title` 链接与 `threadRef` 标记。

## 风险与应对

- **失控的扇出。** 与 `create_bot` 相同的上限形态；每机器人槽位限制约束实际能运行的数量；排队的线程可见，且可从输入框队列中取消。
- **对等方看到不该看的线程。** 作用域按开启者划分，在查询中强制执行，并用反例测试。
- **人丢失当前位置。** 绝不激活机器人开启的线程。
- **机器人撰写的标题被用作注入行。** 使用与名册和来源说明相同的扁平化处理；标题是标签，绝不是提示词文本。
- **对没人记得开启过的线程的信任。** 开启者标签和第一条消息上的来源说明。

## 不在本计划内

跨机器人线程搜索、所有开放线程的看板视图（Hermes 式 kanban）、在线程间移动机器人，以及群组成员的独立执行。每一项都是真正的后续工作；PM 到 QA 的场景都不需要它们。
