# 审批级别

审批级别属于某个 bot，作用于其下一次 provider 轮次，包括该 provider 恢复已有原生线程时。每个级别都是 provider 自身的一种权限模式，原样透传。到达你这里的原生工具请求，是 provider 留给你处理的。OpenMausBot 只依据明确授权作答：完全访问、已保存的精确命令或 MCP 读取型工具，或"替我审批"下内置的窄范围网页搜索许可。在完全访问下，OMB 也会直接应用自身的配置工具，无需再次审批。

| 级别 | 行为 |
| --- | --- |
| **请求审批** | 对命令和文件更改请求审批，与 provider 的受监督模式一致。 |
| **自动接受编辑** | 自动批准文件编辑；其他操作仍可能需要审批。仅在 provider 提供该模式时提供（Claude、Grok、Antigravity）。 |
| **替我审批** | 在 Codex、Claude、Cursor 和 Grok 上使用 provider 的自动审查来批准常规操作，其余操作仍会询问。没有等效机制的 provider 回退为询问。 |
| **完全访问** | 启用 provider 的宽松模式，适用于命令、编辑和选定计算机操作，包括可能具有破坏性或敏感的工作。残留的原生权限提示会替你作答。OMB 配置文件更改、常规操作、团队设置、bot 删除以及已启用技能的编写无需二次审批。在 bot 的授权范围内跳过同行评审提示。通过 `coordinate_bots` 交接的工作使用接收方 bot 的设置，绝不使用发送方的——除非来自 Chief of Staff，其级别会向下传递（见下文）。实际问题与缺失的凭据仍需你输入。 |
| **自定义（`config.toml`）** | 仅 Codex。OpenMausBot 读取并重新应用你 Codex 配置中生效的审批与沙箱设置。 |

完全访问在你选中的那一刻即生效：没有确认对话框，没有第二步。任何能访问应用 API 的客户端都可以开启它：桌面应用、浏览器、已配对的手机或 Web 客户端，或调用本地 API 的 bot 或脚本（本地调用视同你本人：开发环境、CLI、自托管服务器）。在 bot 设置中选中，会立即作用于该 bot 及其所有现有线程；在编辑器中选中，只作用于该线程；刷新权限会将其复制到某个线程。无法运行完全访问的引擎仍无法被设为该级别。在托管式公司工作区中，完全访问仍只能来自运营方的专用策略（[受保护消息](verification/guarded-messages.md)）。

自定义则不同：只能在打包的本地桌面应用中进入或退出，该选择走私有进程通道而非 bot 可访问的 HTTP API，因为它承载的是你自己编写的限制。它在开发环境、独立 Web 和远程页面中隐藏。

团队的侧边栏菜单中有 **为团队中所有 bot 设置…**，供所有者或管理员使用。它会在该团队的所有 bot 上设置一个审批级别（请求审批、自动接受编辑、替我审批或完全访问），或一个模型与推理强度。它会在任何更改发生前列出每个 bot 将获得什么，然后逐个保存 bot，使用相同的请求和与各 bot 自身设置相同的检查。正在工作的 bot，或其引擎不提供该级别、模型或推理强度的 bot 会被跳过，摘要会给出原因。被跳过的 bot 之后不会被更改：其轮次结束后，请重新运行团队更改，或在该 bot 自身的设置中设置。级别会作用于每个 bot 及其所有线程，对所有级别方式相同，因此用"新建线程"打开的线程也会随之移动；只有当 bot 的所有线程都已设置时，该 bot 才算"已设置"。在这台计算机上为某个 bot 选择自动，会显示与其自身设置相同的警告。模型更改会让每个 bot 保持在自己的引擎上，并移动使用该 bot 模型的线程；拥有自己模型的线程会保留它，包括屏幕上打开的那个（相比之下，bot 自身的设置会让该线程随 bot 移动）。自定义仍是按 bot 的设置：处于自定义的 bot 或线程只能在桌面应用中退出。

完全访问不会绕过操作系统隐私控制、身份验证、CAPTCHA 或 MFA、服务权限，或工作区/团队所有权与计算机共享授权。完全访问控制的是审批提示；它不会替你登录、启用你已禁用的功能，或授予另一个 bot 访问其他工作区的权限。

生效设置属于来源对话。已有的"请求审批"线程即使 bot 默认为完全访问，仍保持请求审批；完全访问线程即使 bot 默认为请求审批，也无需这些额外提示即可工作。请求审批、自动和自定义保留其现有的 OMB 配置审查卡片。完全访问操作返回已应用的结果并留下已结算回执，因此 bot 在同一轮次中继续。无效输入、服务不可用或写入失败会返回错误，而不是再次请求审批。过期的原生权限请求不会被变成另一张允许/拒绝卡片。

由 webhook、例行任务或另一个 bot 启动的轮次，会像其他轮次一样在该 bot 的级别下运行。决策日志会记录此类轮次发起时无人在键盘前。

### Chief of Staff 的级别覆盖其委派的工作

审批曾是团队所有者一天中耗费时间的地方：Chief 引入的每个队友都从"请求审批"开始，因此所有者要么每隔几分钟回答一张卡片，要么手动切换每个新线程。因此 **Chief of Staff 的级别会向下传递**。它通过 `coordinate_bots` 分派的工作——进入 Chief 对话与某队友的工作线程，或用 `thread: "new"` 新建的线程——会从该 Chief 对话的级别开始：自动接受编辑、替我审批或完全访问。队友的线程会切换到该级别并保持，打开时有一行说明（"替我审批——由 Clive 委派，一位处于替我审批的 Chief of Staff"）；你仍可在该线程中更改它。Chief 在房间内分派的工作，在该轮次以 Chief 的级别运行。级别在写入分配时计算一次并记录在其上（docs/runtime-contract.md §3）；该轮次正是以该级别运行。

它只会提升：已处于更高级别的队友保持其级别，处于自定义的队友保持自身配置，而从"请求审批"对话分派工作的 Chief 不传递任何级别。队友的引擎会限制级别：没有完全访问的引擎获得替我审批，没有自动接受编辑的引擎（Codex，其请求审批已会写入工作区）保持自身级别。队友自身的默认值及其其他对话不变，普通 bot 的交接仍使用接收方的设置。咨询（`consult: true`）根据队友所知作答且不执行任何操作，因此不随其传递任何级别。问题与缺失的凭据仍会到达你这里。

## 应答请求

在对话中批准或拒绝请求，让 bot 继续。**仅允许一次**只应答本次请求。**本会话始终允许**会把 provider 自身记住的批准交给它：Claude 收到其建议的权限规则，Grok 等 ACP 代理收到其 `allow_always` 选项，或由驱动为该精确操作重复你的答案，直到原生会话结束。API 模型（OpenAI 兼容、MiniMax、Mistral、Grok API）没有原生会话，因此其驱动会在该对话剩余时间内，为该 bot、该精确工具和该精确服务器（按启动时计：更改命令、URL 或凭据即为另一台服务器，而进入 VM 或 Boat 的桥接每轮都是新的）在内存中保留允许，直到服务器重启。同一房间中的另一个 bot 会再次询问。

对于来自已配置自定义 MCP 服务器的读取型工具，卡片还会提供 **始终允许**。这是针对该精确 bot、provider 实例、MCP 服务器、工具名称和当前服务器配置的明确长期授权。不同的工具仍会询问；编辑服务器命令、URL、标头或凭据会使授权失效。对于创建/更新/删除类工具、计算机控制、沙箱更改、未配置的服务器或访客的轮次，不提供此选项。自定义 MCP 服务器控制其自身的工具名称，因此只记住来自你信任的服务器的工具。该授权作用于 bot 当前及未来的对话，包括新委派的工作。已保存的条目可在 bot 的访问设置中查看和撤销。

harness 自身的 agents 工具（协调队友、线程、记忆）在 Claude、Codex 或 API 模型上从不询问：OpenMausBot 自行授权这些路由中的每一个。

自动接受编辑和请求审批会为 provider 询问的任何内容出卡片。替我审批会为 provider 的审查者留给你处理的内容出卡片，并附注"provider 要求你批准此操作。"沙箱扩大在除完全访问外的所有级别都会被拦下。

### 原生审查者从未启动时

Claude Code 对所有模型都接受 `--permission-mode auto`，而当会话无法使用自动模式时，会以手动模式启动且不报错。在 Claude Code 2.1.266 上，Claude Haiku 4.5 和 Sonnet 4.5 以及任何设置了 `disableAutoMode` 的组织就是这种情况。在该会话中，除非你已明确记住该精确的 MCP 读取工具，否则 bot 会在每个操作前询问。Claude 驱动会从 CLI 的 `init` 帧读取会话实际运行的模式；当请求了替我审批而会话运行手动模式时，聊天会每个会话显示一条通知，指明模型。请选择审查者支持的模型、记住你信任的 MCP 读取，或使用完全访问来停止提示。

### 更改 bot 的引擎

处于 **完全访问** 的 bot 在切换到另一个能运行完全访问的引擎时会保持该级别：不会重置为请求审批，也不会确认。跟随其模型的 bot 线程也保持其级别。**自定义** 规则属于 Codex，因此自定义 bot 在更改引擎前会回到请求审批。切换到无法运行该 bot 级别的引擎（例如 Codex 上的自动接受编辑）仍会要求先选择请求审批。

### Antigravity：请求审批、编辑或自动（完全访问）

对于 Antigravity，编辑器和 bot 设置提供 **请求审批**、**自动接受编辑**（其原生 `auto_edit` 模式）和 **自动（完全访问）**。自动会启用原生 `yolo` 模式，并自动批准命令、编辑和计算机操作中剩余的工具有权限请求，无需自动审查者。编辑器标签显示 **自动**。这是换了个名字的完全访问级别，不是单独的权限设置，像完全访问一样立即生效，并覆盖该 Antigravity 实例中的所有模型，包括 Gemini。

请明确选择自动。旧的 Antigravity `auto` / `autoApprove` 设置仍表现为请求审批，并显示为请求审批；升级时它们绝不会变成不受限访问。切回请求审批会在下一轮恢复提示。问题与缺失凭据表单仍需作答。Chief 或队友可以通过 `coordinate_bots` 向该 bot 交接工作，而不会降低其明确的自动（完全访问）授权。它不会在任何其他 bot 上启用自动。

## 向你提问

每个引擎都能停下并提问，且任何审批级别都不会替你回答提问：请求审批、自动接受编辑、自动和完全访问都会留下问题卡片给人工。各引擎的区别仅在于提问的传递方式：

| 引擎系列 | 提问的传递方式 | 同时多个问题 |
| --- | --- | --- |
| Claude Code | 结构化往返（其自身的 `AskUserQuestion`） | 是——CLI 上限为 4 |
| Codex | 结构化往返 | 是——最多 6 |
| Grok Build、Minimax、OpenAI 兼容端点 | 注入的 `ask_user` 工具 | 是——最多 6 |
| ACP 引擎（Cursor、Antigravity、Gemini CLI、Qwen Code、OpenCode 等） | ACP 权限请求上的选项匹配往返 | 一次一个——请求只携带一组选项 |
| Pi | 通过 `extension_ui_request` 的自由文本往返 | 一次一个 |

较旧的对话可能仍保留一个由已移除的 Computer 引擎从模型生成的输出中解析出的问题，而非真正的工具调用。这些卡片保留其"Agent 编写的问题"徽章，其决策日志行保留 `origin: output`。扁平客户端（通知、较旧的配套构建）仅在卡片提出单一选择题时看到普通按钮；多问题卡片会在当前应用上渲染其结构化表单。

## Provider 映射

| Provider | 请求审批 | 自动接受编辑 | 自动 | 完全访问 |
| --- | --- | --- | --- | --- |
| Codex | `on-request` 审批、`workspace-write` 沙箱，由你审查 | 不提供（请求审批已会写入工作区） | 相同沙箱，原生 `auto_review` 审查者 | `never` 审批、`danger-full-access` 沙箱 |
| Claude | 原生 `default` | 原生 `acceptEdits` | 原生 `auto` | 原生 `bypassPermissions` |
| Cursor | 原生默认 | 不提供 | 原生 `--auto-review` | 原生 `--force` |
| Antigravity | 原生 `default` | 原生 `auto_edit` | 旧版 `auto` 表现为请求审批；UI 自动选择完全访问 | 原生 `yolo` 加自动批准剩余工具有权限请求；显示为自动 |
| Grok Build | 原生 `default` | 原生 `acceptEdits` | 原生 `--permission-mode auto`；Grok 审查者的可用性取决于其功能推出情况 | 原生 `bypassPermissions` 加自动批准剩余工具有权限请求 |
| OpenCode | 请求审批 | 不提供 | 请求审批 | 批准单个 ACP 权限请求，绝不批准任务问题 |
| Qwen Code | 原生 `default` | 原生 `--approval-mode auto-edit` | 原生 `--approval-mode auto`（Qwen 的 LLM 分类器批准安全操作，阻止有风险操作） | `--yolo`，加自动批准剩余 ACP 权限请求 |
| Gemini CLI | 原生 `default` | 原生 `--approval-mode auto_edit` | 请求审批（无审查者） | `--yolo`，加自动批准剩余 ACP 权限请求 |
| 其他/自定义引擎 | 请求审批 | 不提供 | 请求审批 | 在实现 provider 映射前不提供 |

这些设置每轮都应用，包括恢复的对话。在提权状态下切换到其他 provider 需要先退出完全访问/自定义；请选择请求审批。在 Antigravity 内切换模型会保持所选级别。原生模式需要支持它们的 CLI 版本；当某个模式被拒绝时，OpenMausBot 不会静默替换为不受限访问。

### 只读集成工具

OpenMausBot 内置的 agents MCP 服务器用明确的只读、非破坏性、幂等、封闭世界元数据描述其限定范围的读取：`list_bots`、`list_rooms`、`list_threads`、`assignment_status`、`session_search`、`session_read`、`list_routines` 和 `skills_list`。会话召回仍强制仅限本 bot 访问，并记录其现有的房间披露审计。这些提示不会授予访问另一个 bot 对话的权限。写入、凭据请求、提案和第三方工具不继承这些提示。该元数据对使用此集成的每个引擎可用；引擎是否使用它取决于该引擎的行为。第三方服务器的任意 MCP 显示标题或 `readOnlyHint` 声明不是绕过提示的授权。

该级别集遵循 [T3 Code 的权限模式](https://github.com/pingdotgg/t3code/blob/e16b8b059c9f5ff6dfed1addecffb831c6aee043/docs/user/permission-modes.md) 中的 provider 边界方法：受监督、自动接受编辑、自动和完全访问，每个都是 provider 模式而非应用规则，并带有属于 provider 会话的记忆批准。其更安静的默认值是完全访问；OpenMausBot 保留请求审批为默认值，而完全访问只需一次选择，无需确认即可应用。

## 面向贡献者的验证

[完全访问工作流配方](verification/full-access.md)通过真实服务器和 MCP 代理测试即时的配置文件、例行任务、团队、技能和同行操作。其夹具还验证明确的请求审批同级线程仍会等待。

运行 `pnpm exec electron scripts/smoke-approval-modes.cjs`，在一次性夹具中演练真实的私有桌面到服务器授权协议。它验证完全访问通过 HTTP 应用而自定义在那里被拒绝、恢复的 Claude 轮次上的完全访问 → 自动 → 请求审批，以及跨多个模型变体的新轮次和恢复的完全访问轮次上的 Antigravity 自动工具批准。它还检查请求审批和旧版自动仍会提示、同行启动的完全访问轮次自动批准、将接收方 bot 切回请求审批即使对完全访问发送方也恢复提示、委派的 Codex 自定义一致地使用原生自动审查者，以及问题保持可交互。Provider 进程是脚本化的假实现；这不会验证实时账户资格或 provider 自动审查者的质量。不使用任何实时用户数据。Grok 覆盖演练跨新/恢复自动轮次的两种模型选择、脚本化原生审查者下的真实内置 MCP 读取、返回请求审批，以及被拦下的删除、凭据、伪造标题命令和问题请求。
