# 持久化响应性

这是一项渐进式并发加固工作，不是从 SQLite 迁移，也不意味着所有持久化操作都是非阻塞的。

## 可重复的合成基准测试

```sh
pnpm bench:persistence
pnpm bench:persistence --worker
pnpm bench:persistence --checkpoint-seed --paced
pnpm bench:persistence --checkpoint-seed --paced --worker
```

每次调用都会创建并删除自己的临时数据目录。只有在 `OMB_DATA_DIR` 指向该目录后才导入配置。它播种 50 个线程，每个线程约 1,000 条 1 KB 消息，然后测量 1、10、50 个会话的突发。每个会话每批写入一条消息并发布十个规范文本增量事件。混合场景还执行五次缺失查询子串扫描。计时前先预热 worker。不使用任何真实引擎、提供商、账户或用户数据。

基线使用相同的同步 SQL 搜索实现；`--worker` 通过新 worker 运行完全相同的查询。SQL 时间、每操作最大值和事件循环延迟是独立的测量项。突发在批次之间让出；它们不是 50 个活跃模型，也不是生产容量估算。在空闲主机上串行运行对比，不要与构建或其他基准测试并行。

循环直方图在工作前启用，工作后清空，以便采样到最终的同步停顿。只报告其最大值；空闲的启用/清空样本会稀释百分位数，因此移除了之前的诊断 p99。

`--checkpoint-seed` 对夹具构建做检查点，并在计时区域外等待一秒；它不改变生产检查点策略。`--paced` 使用 100 个批次，间隔 20 ms，每会话每批一个规范增量和一个原生增量，每 50 批提交一条消息。搜索仍运行五次并被等待，因此其持续时间会延长工作负载：这测量的是事件循环响应性，而非固定速率吞吐量。原始规范追加最大值与整个日志批次分开报告。两种模式都不注入磁盘争用，也不证明主机空闲。

## 2026-09-26 观察结果

macOS arm64，Node 26.7.0，基线 `d1d6bc701` 加上此变更。三次串行基线/worker 对比，播种 50,000 条消息：

| 混合工作负载 | 三次最大事件循环延迟的中位数，同步 | Worker |
| --- | ---: | ---: |
| 1 会话 | 70.84 ms | 3.22 ms |
| 10 会话 | 73.14 ms | 9.77 ms |
| 50 会话 | 90.11 ms | 25.90 ms |

搜索本身保持约 65–85 ms：此变更在扫描运行时释放服务器；它不加速 SQL。此主机上普通写入 p95 通常为 0.11–0.19 ms。

不要隐藏离群值：50 会话混合运行在基线上达到 492.04 ms，使用 worker 时为 292.55 ms。仅写入突发（此补丁未改变）也偶尔出现数百毫秒的停顿。后续归因运行在十次事件发布中测得 455.55 ms；一次 GC 追踪运行测得一次 1,267.99 ms 的消息追加和 417.27 ms 的事件批次，但没有对应的长时间 major-GC 暂停。磁盘/操作系统波动仍然相关；这些不能证明每次停顿都是 SQLite 或生产回归。

### 分离夹具构建与节奏化工作

另外三对串行基线/worker 使用 `--checkpoint-seed --paced`，包括原生日志和规范事件：

| 节奏化混合工作负载 | 最大事件循环延迟中位数，同步 | Worker |
| --- | ---: | ---: |
| 1 会话 | 99.81 ms | 3.47 ms |
| 10 会话 | 102.11 ms | 9.04 ms |
| 50 会话 | 107.22 ms | 25.99 ms |

在这六次调用中，仅写入/日志场景的事件循环最大值为 4.97–30.41 ms；测得的最大消息追加为 6.17 ms，最大日志批次为 22.64 ms。之前数百毫秒的停顿在此节奏化/检查点化工作负载中未复现。节奏化和种子检查点都改变了，因此这不能隔离各自的单独影响，也不能证明之前的停顿仅是设置 I/O。它确实强化了搜索发现，但不构成全面异步写入器/日志器重写的理由。

## 范围与不变量

- 只有 `/api/search` 扫描移到 worker。Agent 召回、消息提交、事件日志和报告/备份工作不会被静默改变。
- 一个惰性只读 worker；最多八个未完成搜索和 30 秒截止时间。忙碌/中断/失败的搜索返回可重试的 503，绝不阻塞回退，也不在失败后返回空成功。
- 字面子串、通配符转义、片段、顺序和线程范围共享现有查询实现。无 Schema 或数据格式变更。
- 异步扫描后再次检查授权和机器人可见性。已删除的对话针对当前 Store 解析。
- 维护/关闭等待 worker 终止。扫描打开/关闭其只读连接，避免工作区替换后出现陈旧文件。
- 消息提交和分支头事务仍在确认之前。

## 验证命令

```sh
pnpm exec vitest run server/message-search-worker.test.ts server/message-db.test.ts server/message-search.e2e.test.ts server/bot-visibility.e2e.test.ts server/workspace-backup.test.ts
pnpm exec vitest run server/index.test.ts -t 'searches transcripts and exports'
pnpm test:packaged-server
```

搜索夹具使用标准隔离启动器，仅播种其新数据库，通过 `control:omb` 发送两个真实的假引擎轮次，执行十六次 HTTP 搜索，等待队列满 503 证明八个被接纳，然后检查在已接受的扫描全部完成前健康响应到达，并验证两个已结算回复和范围化活跃分支搜索结果。它打印保留的证据 JSON/日志路径并删除一次性数据。可见性夹具显式预加载仅测试用的结果屏障。它等待真实 worker 返回私有命中，更改该机器人的受众，然后释放投递并断言没有私有结果泄漏。不假设任意扫描持续时间或请求到达顺序，也不捆绑任何 Hook。作为负面检查，临时复用 await 前的可见性集合使此测试因私有 Payroll 命中而失败；恢复新集合则通过。临时回归不属于此变更。
Worker 测试覆盖一致性、已提交写入/删除、队列边界、超时、只读失败和数据库替换。打包冒烟测试在检出目录外调用搜索，没有可用的 `node_modules`。

历史种子每 1,000 次插入让出一次，以便慢速测试磁盘不会饿死 HTTP 客户端的套接字关闭处理。Windows CI 在设置后暴露了 `ECONNRESET`；一次隔离复现在机器人创建后阻塞客户端八秒产生了相同错误。将该设置延迟拆分为 50 ms 块并让出事件循环，使后续发送正常结算。这仅改变夹具构建，不改变生产请求、搜索负载、超时或断言；未添加请求重试。

## 剩余工作（不在此仅搜索变更范围内）

1. 在隔离磁盘争用下归因写入/日志尾部延迟，并测试真实混合 HTTP 流量、长历史水合、内存刷新和备份。
2. 对于日志变更，保留脱敏、有界缓冲、失败标记、有序记录、检查/备份刷新和删除而不复活。
3. 仅在剩余测量证明合理时移动消息写入。保持事务/回执/取消的持久性边界和有界队列；不要将提交变成即发即忘的写入。
4. 独立测量 Admin：分布式桌面不共享聊天数据库。

本地 macOS 测量不暗示任何实时部署、提供商加速、机队规模承诺或 Windows/Linux 原生验证。
